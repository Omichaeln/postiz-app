# Runbook: restore a single tenant

**When:** accidental deletion or corruption limited to one tenant.
**Owner:** platform on-call, with the tenant's owner or admin (step 5 is their command). **Exercised:** locally by `apps/worker-core/src/runbooks.integration.test.ts` ("restore a single tenant (7.11)"): publications waiting, claimed with an open attempt, sent and pending on the channel (`processing`) and published at the restore point; a tenant-scoped dump of every tenant table (the restore point), a brand deletion and an accidental loss of publications after it, both kill switches engaged tenant-wide, the rows re-imported parents first and only where missing (the lost publications come back), `publishing.publications.holdRestored` called in bounded batches until `hasMore` is false, moving the never-sent rows to `held` and the sent one to `outcome_unknown` with a reconcile request (published, failed, cancelled and already-held rows untouched; a second call moves nothing), the waiting workflow ending on the held row, the pre-restore run unable to send or finalise and its token-less calls failing as non-retryable, and reconciliation finding the live post (→ `published`, no second post), deletion requests made after the restore point re-applied (`deletion.reapply` + the deletion workflow: the deleted brand is gone again), the other tenant byte-for-byte untouched. The command's own guarantees are in `packages/modules/publishing/src/publishing.integration.test.ts` ("restore rule … holdRestored": including the pre-send fence committing `sentAt` while the command waits for the row lock). **Needs a live environment for:** the PITR restore into a separate instance, object version restore, the Temporal namespace restore and the staging harness run (ledger 7.3).

1. Restore the database point-in-time copy to a **separate** instance (never over production).
2. Export the tenant's rows from the copy (every table has `tenant_id`; `pnpm check:schema` lists the exceptions) with a tenant-scoped dump.
3. Object storage: restore `assets/{tenant}/...` and `releases/{tenant}/...` object versions for the window.
4. Import into production inside a maintenance window for that tenant only (kill switches `release_dispatch` and `agent_starts` engaged tenant-wide first; approval-path posts are not stopped by them, see step 5). Import parents before children (foreign keys) and only rows missing in production.
5. **Restore rule (spec 17.6):** move every restored publication in `scheduled`/`dispatching`/`processing` out of flight and reconcile each against remote history before release, so a restore cannot republish. Signed in as the tenant's owner or admin (policy `billing.manage`; agents are refused), call `publishing.publications.holdRestored` with `{ "brandId": null }` for the whole tenant, or a brand id to restrict it to one brand (`brandId` is required; optional `limit`, default and maximum 200). Each call handles at most `limit` rows in its own transaction and returns `{ held: [publicationId, …], outcomeUnknown: [publicationId, …], hasMore }`: **call it again until `hasMore` is `false`**, adding up the lists (each row appears once across the calls). Per row: never sent (`scheduled`, or `dispatching` whose attempt has no `sentAt`) → `held` with hold reason `restored_from_backup`; possibly live (`processing`, or `dispatching` whose attempt has `sentAt`) → `outcome_unknown` with state reason `restored_from_backup` and a `publication.reconcile_requested` event, which starts `publicationReconcileWorkflowV1` (spec 14.3 reconciliation: the remote post found → `published`; proved absent → `retry_eligible`; undetermined after +1 h → `held`, reason `outcome_unknown_unresolved`). Every moved row gets a `publication.hold` or `publication.outcome_unknown` audit event and a `publication.state_changed` outbox event. A claimed row's fencing token moves on: the run that still holds the old claim is refused (`VALIDATION_FAILED`, `stale_fencing_token`) wherever it presents the token, so it can neither commit `sentAt` (nothing is sent) nor poll or finalise; its token-less calls on a held row fail as a non-retryable `ValidationFailed` activity failure, so that workflow run fails once, without retries, and leaves the row as the command set it (in Temporal it shows as failed; that is expected). A waiting workflow re-reads the row and ends. The command is idempotent: a partial run (an error, a timeout) keeps the batches that committed, and calling it again, also after any late import, moves only what is still in flight. Then, per row:
   - `held` (never sent): check the channel anyway; release it with `publishing.publications.reschedule` (the calendar's **Release again**, which re-runs the release checks and starts a new workflow generation), or cancel it (`publishing.publications.cancel`).
   - `outcome_unknown` (possibly live): let reconciliation run, or resolve it by hand as in [reconcile an outcome_unknown publication](reconcile-outcome-unknown.md): if the post is on the channel, `publishing.publications.reconcile` with `confirm_published` and its remote post id (→ `published`, never re-sent); if you are sure it is absent, `confirm_absent` (→ `retry_eligible`), then release it with `reschedule`. Never cancel a row that is live: the record would say it was not published.
   - `held` with `outcome_unknown_unresolved` (reconciliation gave up): look for the post; if absent, release it; if present, cancel the row with `reconcile` `cancel` and record the remote post in the ticket (the machine has no `held → published` move).
6. Re-apply deletion requests made after the restore point: for each (`deletion_requests.created_at` after the point), `deletion.reapply` then re-run `deletionRequestWorkflowV1` for it (docs/runbooks/process-deletion-request.md). Requests still open at restore time simply resume.
7. Verify: cross-tenant harness on staging against the restored data; the tenant's owner confirms; release the kill switch.
